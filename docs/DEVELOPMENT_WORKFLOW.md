# 開発時の注意点

## 基本方針

ユーザーの他の作業を妨げずに開発する。通常利用中のMyToolBoxを繰り返し開いたり、前面に出したり、終了・再起動したりしない。開発と本番反映を分け、デプロイはユーザーが変更をまとめて実施する。個別機能の開発依頼を、本番反映の依頼と解釈しない。

## 通常の検証

1. 純粋ロジックの単体テストで正常系・境界値・失敗時を確認する。
2. UIの状態遷移は、実際の画面が使うモデルを専用プローブから検証する。保存先・UserDefaultsはテスト用に隔離し、利用中のメモ・タイマー・設定を変更しない。
3. 見た目は実際のSwiftUI／AppKit部品をオフスクリーン描画し、生成画像で確認する。通常利用のメイン画面やツール一覧を開く必要はない。
4. [TESTING.md](../TESTING.md)に従いFast → Fullを実行する。Fullはビルド・署名確認までであり、配置・起動は含まない。

既存の入口は`Tests/MonitorKitTests`、`tools/VerifyAddedTools.swift`、`tools/VerifyQuickMemo.swift`、`tools/VerifyPersonalCalendar.swift`、`tools/RenderLocalTools.swift`など。コンパイル方法と対象別の手順はTESTING.mdを正本とする。新しい共通テストランナーは本方針の記録時点では追加していない。

プローブも実装を確認してから実行する。`orderFront`・`makeKeyAndOrderFront`・アプリのactivate・グローバルキー登録・クリップボード操作・音声／マイク開始・本番設定への書込みを含むものは、そのままバックグラウンド検証と扱わない。既存の`ThemeSwitchProbe`は`orderFront`を使うため、通常の裏側検証には含めない。

UI変更は実画面と同じモデル・Viewを使って検証する。検証専用の模倣UIだけで成功と判定しない。API・OS取得値の欠損を仮の成功値で隠さず、合成データによる描画と実測を区別する。

## 実画面が必要な場合

IME、フォーカス、ドラッグ＆ドロップ、ファイルパネル、物理ショートカット、実機固有の表示など、裏側では確認できない項目は未検証として記録する。画面操作が必要なら対象と理由を伝え、ユーザーが明示的に依頼した範囲で対象画面だけを確認する。実画面確認のために本番アプリを毎回更新しない。

## 完了報告と本番反映

開発完了時は変更内容、実行した検証、失敗・未実施の項目、本番未反映であることを報告し、[sessions](../sessions/README.md)に短く残す。ビルド成功をデプロイ済みと記録しない。

本番の`/Applications/MyToolBox.app`へのコピー・差替え、通常利用中の本体／独立ツールの終了・再起動、ログイン登録や権限設定の変更は開発作業に含めない。デプロイはユーザーがまとめて行う。後からユーザーが明示的に代行を依頼した場合だけ、その範囲で対応する。

一括反映時の署名・保存状態・最新版保持と、成功後のビルド出力整理は[OPERATIONS.md](../OPERATIONS.md)に従う。反映前の検証用ビルド出力は開発成果物として扱い、日時付きの本番.appコピーを増やさない。
